## How the merges went
- **The usual command failed.** `gh pr merge 2 --merge` returned: "This pull request is part of a
  stack and must be merged using the asynchronous merge REST API".
- **Docs for the async merge**
  (https://docs.github.com/rest/pulls/pulls#merge-a-pull-request-asynchronously, read 2026-10-17):
  - `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge-async` "is the required API for merging
    stacked pull requests";
  - `merge_method` is "Only supported for direct merges";
  - a 202 means the merge "will run in the background".
- **PR #2.** Merged with `merge_method=merge`, `merge_action=direct_merge` and `sha` = `70583c9`: 202,
  then `merged`. The merge commit is `c7fe9e8`, with parents `4fb3094` and `70583c9`.
- **GitHub rebased the Phase 2 branch.** It then pointed PR #3 at `main` and rebased its branch
  itself. The new head is `47e9a59`, every commit has a new id, and the merge commit `eab5ff2` was
  dropped. The file tree is identical to the tested `90de666`. GitHub's page "Merging stacked pull
  requests"
  (https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests,
  read 2026-10-17) says: "After the merge, the next unmerged pull request is automatically rebased to
  target the stack base directly". It also requires a linear stack, offering a "Rebase stack" button
  otherwise, which is why the web page pointed to `gh stack`.
- **PR #3.** Merged the same way (`sha` = `47e9a59`). The merge commit is `0d57694`, with parents
  `c7fe9e8` and `47e9a59`.
- **Result.**
  - All three PRs are MERGED.
  - `main` (`0d57694`) has exactly the tested content: `git diff 90de666 origin/main` is empty.
  - `uv run pytest` on `main`: 155 passed; ruff clean.
- **Lesson:** GitHub's stacks are rebase-based, which clashes with our no-rewrite rule. CLAUDE.md now
  says to keep one open phase PR at a time.
